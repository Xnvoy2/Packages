# Packages: architecture

What the system is, what it trusts, and where the edges are. Read
[README.md](README.md) to run it and [DEPLOYMENT.md](DEPLOYMENT.md) to ship it.

---

## What the product does

An npm package gets a public identity that connects:

```
PACKAGE -> PUBLISHER -> CODE -> RELEASE HISTORY -> CONTRIBUTORS -> WALLET -> SOLANA RECORD
```

It issues no token, runs no market, and sells nothing. The only claim it makes
is about who publishes a package, and the whole system is arranged so that
claim is backed by evidence rather than assertion.

---

## Shape

Three processes, no framework.

```
  browser
     |  (one origin)
     v
  tools/serve.js ──── static html, css, js ──── assets/
     |  proxies /api in development
     v
  api/index.js ──── node http, no framework
     |         \
     |          \──── registry.npmjs.org, api.npmjs.org
     |           \─── api.github.com
     |            \── api.devnet.solana.com   (read only)
     v
  PostgreSQL
```

The site is static files. Every page is generated by `tools/build.js` from a
body in `src/pages/` plus shared chrome; **the root `*.html` files are output
and must never be edited**. All data arrives from the API at runtime through
one seam, `assets/js/api.js`; nothing else in the front end calls `fetch`.

The API is plain `node:http` with a route table. It has no ORM: the SQL is
visible at the call site.

### Why one origin

The session cookie is `HttpOnly` and `SameSite=Lax`, and a Lax cookie is not
sent on a cross-origin fetch. A site on one domain calling an API on another
could never be signed in. Production puts both behind one domain;
`tools/serve.js` proxies `/api` so development matches rather than diverges.

## The verification model

This is the part worth understanding, because it is the product.

### The problem

The `repository` field in a `package.json` is written by whoever publishes the
package, and **the npm registry does not check it**. Two different people can
publish two different packages pointing at the same repository. So controlling
a repository says nothing about being able to publish a package, and anything
that treats the two as equivalent is making a false claim.

### The rule

In `api/lib/verify.js`, in one function, asserted by an exhaustive test over
all sixteen combinations:

```
verified  <=  publish_proof  OR  (repo_control AND trusted_publisher)
```

Four facts, collected independently, each checked rather than assumed:

| Fact | Established by | Sufficient alone? |
|---|---|---|
| `repo_control` | GitHub reports push, maintain or admin for this user on the repository the package declares | **No.** Yields the status `repo_linked` |
| `trusted_publisher` | npm's own SLSA provenance for a published version names that repository, **compared by GitHub's immutable numeric id** | No |
| `publish_proof` | a single-use string this server issued appears in a version manifest on the registry | **Yes** |
| `maintainer_email_match` | an npm maintainer email equals a *verified* GitHub email | **Never.** Shown as "signal only" |

The id comparison is not fussiness. Both reference repositories moved during
development: `stevemao/left-pad` was transferred to the `left-pad` org, and
`facebook/react` became `react/react`. Both kept their numeric id. A name
comparison would have broken on both; an id comparison did not.

### The publish proof

The server issues a nonce. The publisher adds it to their `package.json` and
publishes a version. Only an account that can run `npm publish` for that
package can put a string into one of its published versions.

Deliberate properties:

- **It costs a real publish.** The interface says so before issuing the
  string: this writes a public, permanent version to npm.
- **No npm credential is ever requested or stored.** The server could not
  publish on anyone's behalf, which is why the proof means something.
- Only versions published *after* the nonce was issued count, so an old
  version containing some string cannot be replayed.
- One outstanding challenge per package per account; asking for a new one
  invalidates the old, so nonces cannot be stockpiled.

### What is never collapsed

Six separate facts, shown as six separate badges, never as one "verified":

```
npm publisher verified · GitHub repository linked · GitHub repository control
verified · provenance available · wallet verified · onchain registered
```

"GitHub repository linked" means a `package.json` field says so. "GitHub
repository control verified" means GitHub confirmed push access. They are
different claims and the interface says which it is making.

## Trust boundaries

| Boundary | What is trusted | Why, and what limits it |
|---|---|---|
| npm registry | that it reports its own publish records honestly | it is the authority on who published what; there is no second source |
| npm provenance | the registry's TLS response | the DSSE bundle's Sigstore chain is **not** verified offline. Hardening noted in the threat model |
| GitHub | permission and repository facts for the signed-in user's own token | the token is the user's; absence of a `permissions` block is recorded as unknown, never as a denial |
| Solana RPC | what the cluster reports about accounts and signatures | three independent facts must agree before anything is marked onchain |
| The registrar key | authorises every onchain write | **the real centralisation.** Verification is off-chain, so the program cannot check a proof itself. The registrar is recorded on every identity account so a reader can see whose word it rests on |
| The browser | nothing | every state change is checked server-side; a client reporting a confirmed transaction produces `TRANSACTION_PENDING` |

## The launch state machine

`api/lib/lifecycle.js`. Eleven states, one derivation, legal moves written
down.

```
DISCOVERED -> CONNECTING -> GITHUB_CONNECTED -> REPOSITORY_VERIFIED
                                  |                    |
                                  +---------> PUBLISHER_VERIFIED -> WALLET_VERIFIED
                                                        |
                                              READY_TO_LAUNCH -> TRANSACTION_PENDING -> ONCHAIN
                                                                        |
                                                                      FAILED
```

Two rules make it trustworthy:

1. **The facts are authoritative, not the state.** The state is computed from
   what has been proved and what the chain says. It is never stored as the
   source of truth, so it cannot drift into claiming something unproved.
2. **Illegal moves throw.** Nothing can skip to `ONCHAIN` except from
   `TRANSACTION_PENDING`; nothing moves backwards; `ONCHAIN` is terminal
   because the program has no instruction that removes an identity account.

`GITHUB_CONNECTED -> PUBLISHER_VERIFIED` skips the repository stage on purpose:
that is the publish-proof route, and it is why a package with no repository is
not locked out.

## Data model

PostgreSQL, migrations in `api/migrations/`, numbered and checksummed. Editing
an applied migration is refused; add a new one.

```
users ──< sessions
  |
  +──< claims >── packages ──< releases
  |       |           |    \
  |       |           |     +──< onchain_registrations
  |       |           |     +──< onchain_releases
  |       |           |     +──< download_snapshots
  |       |           |     +──< package_contributors >── contributors
  |       |           |
  |       +──< verification_events        repositories
  |
  +──< wallets, challenges, audit_log
```

Four invariants the schema and the code enforce together:

- **One active identity per package.** `packages.verified_owner_id`, written
  inside a transaction with `SELECT ... FOR UPDATE`, so two accounts proving
  the same package concurrently cannot both win.
- **Verification history survives.** `verification_events` is append-only.
  Revoking writes a revocation; it does not delete the proof.
- **Onchain records are not overwritten.** A second registration attempt is a
  new row in `onchain_registrations`. `packages.identity_pda` is written once
  and only by a reconciliation that read the chain.
- **Imported facts are distinguishable from verified ones.** Every imported
  row carries `source` and `retrieved_at`.

### Contributor graph

`contributors` and `package_contributors` model who contributed to what, with
the evidence source and retrieval time on every row. **A contributor login and
a signed-in GitHub account are kept separate.** They may well be the same
person; nothing here proves it, and inferring it would be inventing a fact.

There is no reputation score, and the schema is deliberately ready for one
without pretending one exists.

## npm integration

`api/lib/npm.js`. Three public endpoints: search, the packument, downloads.

Handles: scoped names, 2,379-version histories, unpublished versions still in
the `time` map, deprecation (per package and per version), tarball integrity,
provenance attestations, and packages with no repository or no license.

**A value npm does not report is `null`, and `null` renders as a dash.**
Nothing is estimated, defaulted or filled in.

Caching is per endpoint with request coalescing, so four cards asking for the
same package on first load make one upstream request.

## GitHub integration

`api/lib/github.js`. OAuth web flow with a state parameter bound to the
browser by a short-lived cookie; the access token is encrypted at rest with
AES-256-GCM. Repository, contributor, release and commit reads, with
pagination and truncation reporting.

`GITHUB_READ_TOKEN` is strongly recommended: without it the whole server
shares 60 unauthenticated requests an hour, which real traffic exhausts in
minutes. The product degrades honestly when that happens, reporting
`rateLimited` rather than an empty list.

## Solana

`solana/programs/package_identity/` — an Anchor program that holds no funds
and mints nothing.

A package's identity address is a PDA of the sha256 of its name. **The name is
always hashed**, because a Solana seed is capped at 32 bytes and npm allows
214: a literal seed could not address most of the namespace.
`api/lib/solana.js` derives identically, and a test asserts the two are
byte-identical against a fixed vector.

Registration is three calls, because a browser cannot be trusted to report the
outcome of its own transaction:

```
prepare  -> server records intent, returns the derived address and a blockhash
submitted-> client reports a signature; the server records it and believes nothing
reconcile-> server asks an RPC node: did the signature succeed, does an account
            exist at the derived address, and is it owned by our program
```

All three must agree. Existence alone is rejected: anyone can create an
account at a derived address through a different program.

**Status:** the program type-checks and 13 Rust unit tests pass. It has never
been built as an SBF object, never deployed, and no transaction has ever been
broadcast. See [solana/TOOLCHAIN.md](solana/TOOLCHAIN.md) and
[solana/THREAT-MODEL.md](solana/THREAT-MODEL.md).

## Data freshness

`api/lib/refresh.js`. One package at a time, oldest first, only when stale,
with per-package exponential backoff on failure. Only claimed or launched
packages are refreshed; refreshing everything anyone looked up would make this
a crawler.

**A failed refresh never destroys what was known.** An upstream being down is
not evidence about a package. `fetched_at` records the last *success*, and the
API exposes per-package freshness including the last failure, so a page can
say "this is old and the last check failed" rather than showing stale data as
current.

Off by default; set `PACKAGES_REFRESH_INTERVAL_MS` to enable.

## Discovery

Five views over what has actually been indexed: verified publishers, recently
launched, recently updated, active development, most downloaded. Every
response carries its scope, including the sentence that this indexes what
people connected rather than mirroring npm.

**There is no "trending."** Trending needs a measured rate of change, which
needs a run of download snapshots over time. The snapshots are being
collected; the view will exist when they can support it honestly.

## Security

- CSP with no `script-src 'unsafe-inline'`; the build writes the runtime
  config to `assets/config.js` specifically so it does not need it. Plus
  `nosniff`, `frame-ancestors 'none'`, referrer and permissions policies.
- Sessions: a 32-byte random token, of which only the sha256 is stored, so a
  dump of the table cannot be replayed. Logout destroys the row server-side.
- Every input validated before it reaches a query, a path or an outbound url.
  npm's real name grammar, GitHub's owner and repo grammar, base58 for keys.
- Rate limiting per client per route group, with the forwarded-for header used
  only as a key and never as an identity.
- 33 adversarial tests: SQL injection, XSS, CSRF, SSRF, path traversal,
  prototype pollution, open redirects, IDOR, session fixation, replay, and
  that no error leaks a connection string, token or stack trace.

## Testing

```
npm test                                   # pg-mem, no setup
node tools/pg-dev.js                       # throwaway PostgreSQL
DATABASE_URL=<printed url> npm test        # the real thing
```

**pg-mem accepts `BEGIN`/`ROLLBACK` and keeps the rows anyway.** Transaction
and locking tests therefore skip loudly unless `DATABASE_URL` points at real
PostgreSQL, because passing against pg-mem would prove the opposite of what
they claim.

The suite refuses any database whose name does not contain "test", after an
early run left fixture packages marked *verified* in a development database
and the homepage displayed them.

Browser testing is headless Chrome over CDP: every route at 1920, 1440, 1024,
768, 390 and 375, checking console errors, page errors, horizontal overflow,
layout shift, reduced motion and keyboard order.

## Known limitations

- **GitHub OAuth has never run.** There are no credentials. Everything around
  it is tested at the protocol boundary; the code exchange itself is not.
- **The `permissions` block.** Whether GitHub returns it for a token holding
  only `read:user` is unconfirmed. The code records its absence as
  `permission_unknown` and never as a denial — fail-closed, but it needs
  confirming on a real app.
- **Provenance signatures are not verified offline.** The attestation is
  trusted because it came from the registry over TLS.
- **The registrar is a single key.** A multisig is the obvious hardening.
- **Rate limiting is per process.** Behind several instances each enforces its
  own share.
- **`server/` holds an unrelated Patreon backend** from a parallel session.
  Packages lives entirely in `api/` and loads nothing from it. See
  [server/README-OWNERSHIP.md](server/README-OWNERSHIP.md).
